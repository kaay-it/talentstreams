==== ✅ TASK-22: Слияние Candidates и Candidates Database в один лист

*Выполнено:*

*Архитектурное решение:* регистрационная форма и рассылки теперь работают с одним листом (первый лист / «Candidates Database»). Отдельный лист «Candidates» упразднён.

* `CandidateStatus` перемещён в начало `lib/sheets.ts` — используется в типе `Profile`.
* Тип `Profile` расширен регистрационными полями: `status: CandidateStatus | ""`, `activeSince`, `registrationTimestamp`, `coverLetter`, `resumeUrl`. Пустой `status` = legacy-строка без колонки → считается «Активный».
* `KNOWN_KEYS` и `HEADER_ALIASES` дополнены алиасами: `"status"`, `"active since"` → `activeSince`, `"timestamp"` → `registrationTimestamp`, `"cover letter"` → `coverLetter`, `"resume url"` → `resumeUrl`.
* `buildProfile()` читает все новые поля из строки.
* `rowsToProfiles()` (а значит `getProfiles()`) фильтрует: возвращает только строки где `status` пустой или «Активный» — кандидаты «На проверке» и «Отклонён» в рассылки не попадают.
* `appendCandidateRow()` пишет в главный лист (без префикса `'Candidates'!`), case-insensitive сопоставление заголовков — работает при любом регистре заголовков редактора.
* `getCandidates()` читает из `SHEET_RANGE` (главный лист) через `rowToRecord()` — применяет `HEADER_ALIASES` (включая русские алиасы «Кандидат» → `name`, «Статус» → `status` и т.д.), поэтому работает с любым регистром и языком заголовков, которые редактор задал вручную. Пустой статус → «Активный» (обратная совместимость с legacy-профилями без колонки Status).
* `updateCandidateStatus()` обновляет ячейки главного листа.
* `ensureCandidateColumns()` добавляет в главный лист колонки: `id`, `Status`, `Active Since`, `Timestamp`, `Cover Letter`, `Resume URL`.
* `registerCandidate()` генерирует UUID (`crypto.randomUUID()`), передаёт в `appendCandidateRow` с lowercase-ключами для надёжного case-insensitive маппинга.

import { get } from "@vercel/edge-config"

export async function getStreams(): Promise<string[]> {

==== TASK-GC-3: Адаптация Server Actions для записи в Edge Config

NOTE: UI управления стримами уже реализован в TASK-DB-8 (`components/streams-table.tsx`, Server Actions `createStream/updateStream/deleteStream`). TASK-GC-3 — только смена бэкенда записи с Drizzle/Neon на Edge Config API.

Заменить реализацию Server Actions в `app/actions.ts`:

[source,ts]
----
// Вспомогательная функция записи в Edge Config
async function updateStreamsInConfig(streams: StreamRecord[]): Promise<void> {
  await fetch(`https://api.vercel.com/v1/edge-config/${process.env.EDGE_CONFIG_ID}/items`, {
    method: "PATCH",
    headers: {
      Authorization: `Bearer ${process.env.VERCEL_API_TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ items: [{ operation: "upsert", key: "streams", value: streams }] }),
  })
}
----

Все три action-а (`createStream`, `updateStream`, `deleteStream`) читают текущий массив из Edge Config, вносят изменение и пишут обратно через `updateStreamsInConfig`. `revalidatePath` остаётся без изменений.

== Приложение: переход на реляционную СУБД

=== Анализ

Google Sheets достаточен для MVP, но создаёт структурные ограничения по мере роста:

* *Производительность:* каждый запрос — HTTP-вызов к Sheets API; нет индексов, фильтрация только in-memory. При 500+ кандидатах и 100+ работодателях это станет ощутимым.
* *Целостность данных:* нет foreign keys и транзакций — связи между листами поддерживаются вручную (candidateId, employerToken — строки без ограничений).
* *Сложные запросы:* фильтрация, JOIN-подобные операции (подборка → кандидаты → работодатели) делаются in-memory в `lib/sheets.ts`, что увеличивает объём данных, которые нужно держать в памяти.
* *Параллельные записи:* append-only подход с `rowIndex` — хрупкий при одновременных операциях.
* *Лимиты API:* Google Sheets API — 300 запросов в минуту на проект.
