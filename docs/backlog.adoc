==== ✅ TASK-32: История версий резюме в Neon

*Что сейчас было до этой задачи:* когда рекрутер загружал в `CandidateEditModal` новый файл резюме вместо старого (например, после того как кандидату помогли подправить или брендировать резюме), в Sheets просто перезаписывался URL — старый blob-файл в Vercel Blob не удалялся и никуда не девался, но и ссылки на него больше нигде не было: чистый мусор, накапливающийся в хранилище без возможности его найти или использовать.

*Решение:* вместо удаления старых файлов — хранить полную историю версий резюме кандидата отдельно, в Neon, и показывать её в редакторе. Google Sheets по-прежнему хранит только URL последней версии (используется на публичных страницах, в проксировании и т. д.) — ничего в этом контуре не поменялось.

* `lib/db/schema.ts` — новая таблица `candidateResumes` (`id` text/UUID, `candidateId` text, `kind` text — `"file"`/`"link"`, `filename` text, `url` text, `createdAt` timestamp). Миграция `lib/db/migrations/0002_harsh_tomorrow_man.sql`, применена к продовой Neon.
* `lib/db/resumes.ts` (новый файл) — `addResumeVersion(data)` (не пишет, если `candidateId` или `url` пустые — молча пропускает, не бросает) и `getResumeVersions(candidateId)` (новые сверху, `orderBy(desc(createdAt))`). Если `filename` не передан явно и `kind === "file"` — имя выводится из URL через `blobFilenameFromUrl()` (ниже), а не остаётся пустым; для `"link"` фолбэка нет — у ссылки нет «имени файла».
* `lib/sheets.ts` — `Candidate` дополнен `id: string` (то же самое поле `id`/UUID, что уже резолвилось через `HEADER_ALIASES` для `Profile`, просто не попадало в объект `Candidate`, используемый редактором) — нужен как стабильный ключ для истории версий в Neon.
* `lib/blob.ts` (новый файл) — `isOwnFileUrl(url)`: `true`, если URL указывает на собственный Vercel Blob — напрямую (хост оканчивается на `blob.vercel-storage.com`) или через свой прокси `/api/resume?url=<blobUrl>` (тот же паттерн, что уже валидировал `app/api/resume/route.ts` — константа `BLOB_HOST` вынесена сюда и переиспользована оттуда, вместо дублирования). Любой другой URL — «ссылка», введённая кандидатом/рекрутёром вручную. Там же `blobFilenameFromUrl(url)` — берёт последний сегмент пути (`resumes/1754460447259-a1b2c3d4.pdf` → `1754460447259-a1b2c3d4.pdf`); это сгенерированное имя файла в Blob, а не оригинальное имя, под которым кандидат загружал файл — Vercel Blob оригинальное имя нигде не хранит, `put()` вызывается уже с нашим сгенерированным путём.
* `app/actions.ts`:
** `registerCandidate()` — генерирует `id` (как и раньше, `crypto.randomUUID()`, не через внешний скрипт), после успешной записи строки сразу пишет первую версию резюме в `candidateResumes`, если `resumeUrl` не пустой. Благодаря синхронной генерации `id` в этой же функции первый файл кандидата тоже попадает в историю — не только последующие замены через редактор.
** `updateCandidate()` дополнен `candidateId` (обязателен), `resumeVersionChanged?: boolean` и `resumeFilename?: string` — если `resumeVersionChanged` и `resumeUrl` не пустой, пишет новую версию в `candidateResumes` после записи в Sheets. Клиент передаёт `resumeVersionChanged` только когда итоговый `resumeUrl` реально отличается от `candidate.resumeUrl` на момент открытия формы — редактирование прочих полей без изменения резюме новую версию не создаёт.
** `kind` (`"file"` / `"link"`) в обоих случаях вычисляется на сервере через `isOwnFileUrl(resumeUrl)`, а не берётся из клиента — клиент присылает только `resumeFilename` (для файла) и признак изменения; какой именно вкладкой пользовался человек в форме, на классификацию не влияет.
** `getCandidateResumeHistory(candidateId)` — новый экшен, отдаёт историю версий для конкретного кандидата.
* `components/candidate-registration-modal.tsx` / `components/candidate-edit-modal.tsx` — передают только `resumeFilename` (оригинальное имя загруженного файла, только когда реально был выбран новый файл); тип резюме на клиенте больше не вычисляется и не передаётся.
* `components/candidate-edit-modal.tsx` — под блоком «Резюме» новый блок с историей: подгружается через `getCandidateResumeHistory(candidate.id)` в `useEffect` при открытии модалки, разбит на две подгруппы — «Файлы (N)» и «Ссылки (N)» (только непустые), в каждой — список с датой и кнопкой «Открыть» (та же прокси-ссылка `/api/resume`, что уже используется для текущего резюме). Пустое состояние — «История резюме появится здесь после следующей загрузки нового файла или ссылки».
* `scripts/backfill-resume-history.ts` — одноразовый скрипт для кандидатов, заведённых до этой задачи: читает текущих кандидатов из Sheets, для каждого с непустыми `id` и `resumeUrl` пишет одну запись в `candidateResumes` (`kind` — тем же `isOwnFileUrl()`, что и в боевом коде; дата — исходный `Timestamp` кандидата, а не «сегодня», через новый параметр `addResumeVersion({ createdAt })`). Идемпотентен — повторный запуск пропускает уже записанные пары `(candidateId, url)`. Запускается через `NODE_OPTIONS="--conditions=react-server" npx tsx scripts/backfill-resume-history.ts` — импортирует `lib/sheets.ts`/`lib/db/resumes.ts` напрямую (`import "server-only"` иначе бросает исключение вне сборки Next). Прогнан один раз против прод. Sheets/Neon: 87 кандидатов → 77 записей (71 файл, 6 ссылок), 10 без резюме, 0 без id. Скрипт удалён из репозитория после использования — тот же порядок, что и у последующих одноразовых бэкафиллов (`scripts/backfill-employers-to-neon.ts`, TASK-DB-3; перенос Mailing Lists, TASK-DB-5).

*Осознанный трейд-офф:* старые blob-файлы теперь никогда не удаляются — они все остаются в Vercel Blob и все видны в списке версий. Место в Blob растёт с каждой заменой резюме, но взамен ничего не теряется и не требует отдельной политики очистки — сознательный выбор в пользу полноты истории, а не экономии места.

*Не реализовано:* кандидаты, у которых нет `id` (устаревшие строки, вписанные в таблицу вручную до того, как проставился ID) — история версий для них не пишется и не отображается, поле просто не показывается в модалке (`candidate.id` пустой). Восстановления/выбора конкретной старой версии как «текущей» из списка нет — список только для просмотра и скачивания, чтобы вернуть старый файл текущим, нужно перезалить его вручную.

**Донаполнение — история резюме прямо в таблице `/editor/candidates`:** раньше файлы/ссылки были видны только внутри формы редактирования — приходилось открывать карточку каждого кандидата, чтобы узнать, есть ли у него резюме.

* `lib/db/resumes.ts` — `getResumeVersionsForCandidates(candidateIds)`: один запрос (`WHERE candidateId IN (...)`) вместо N отдельных — результат сгруппирован по `candidateId` (объект `Record<string, ResumeVersion[]>`), каждая группа уже отсортирована новыми сверху, т. к. общий `orderBy(desc(createdAt))` сохраняет относительный порядок внутри групп.
* `app/editor/candidates/page.tsx` — вызывает `getResumeVersionsForCandidates()` один раз для всех кандидатов страницы и передаёт карту вниз в `CandidateSection` — без этого список из ~90 кандидатов означал бы ~90 отдельных запросов к Neon при открытии страницы.
* `components/candidate-section.tsx` — таблица `CandidateRow` (было — список карточек `<div>`) с колонками Кандидат / Контакты / Файлы / Ссылки / Дата регистрации / Активен с / Действия. Колонки «Файлы» и «Ссылки» показывают до 3 последних версий каждого типа как компактные чипы-ссылки (иконка + имя файла или домен ссылки, обрезанные `truncate`) — ведут прямо на файл/ссылку, открывать карточку кандидата для этого больше не нужно. Колонка «Дата регистрации» — `candidate.timestamp`, перед «Активен с».

==== ✅ Реальный текст ошибки при регистрации/редактировании работодателя

*Проблема:* при регистрации работодателя с уже занятым email форма вместо понятного текста показывала общую ошибку Next.js: «An error occurred in the Server Components render. The specific message is omitted in production builds…». Реальное сообщение («Работодатель с таким email уже зарегистрирован») было видно только в серверных логах (`digest`).

*Причина:* осознанное поведение Next.js — в production-сборке Server Actions отдают клиенту общий текст для любого `throw new Error(...)`, чтобы не утекали детали непредвиденных ошибок. Это ломает ожидаемые, «бизнесовые» ошибки валидации (дубликат email/телефона, пустые обязательные поля), которые как раз нужно показывать пользователю как есть.

*Решение:* `registerEmployer()` и `updateEmployer()` (`app/actions.ts`) теперь возвращают `{ ok: true } | { ok: false, error: string }` вместо `throw` для ожидаемых случаев валидации. `EmployerRegistrationModal`/`EmployerEditModal` читают `result.error` из возврата; `catch` оставлен только на непредвиденные сбои (сеть/БД) — там по-прежнему общий фолбэк-текст, что корректно.

NOTE: ℹ️ Тот же паттерн — `throw new Error()` для валидации ломает вывод сообщения в production — остаётся в других Server Actions (`registerCandidate`, `createCandidate` и т. д.), но там соответствующие ошибки либо уже гасятся клиентской валидацией (`required`-поля), либо не встречались на практике. Исправлено точечно там, где реально ломалось (дубликат email/телефона у работодателя).

==== ✅ Нормализация contactRequests: FK на employers и streams вместо дублей

Только *имя* защищено — тип и описание остаются редактируемыми всегда, для любого стрима (чисто информационные поля, `type` нигде не используется программно кроме цвета бейджа в UI, ничего вниз по цепочке на них не завязано).

==== TASK-05: Правила публикации кандидатов

*Что сейчас:* видна история рассылок кандидата (см. ниже), но нет автоматического отслеживания статуса паузы и нет защиты от нарушения правил при создании выпуска.

* Первая публикация → фиксируется дата.
* Через 2 недели возможна повторная публикация.
* После *второй* публикации — пауза 3 месяца (не после первой — частая ошибка при пересказе правила).
* Кандидат может попросить статус «Не публиковать».
* Если дата следующей разрешённой публикации не наступила — кандидата нельзя включить в выпуск; система должна показывать эту дату.

*Что уже сделано (видимость, первый инкремент):* `CandidateEditModal` показывает блок «История рассылок» — каждый выпуск, в который кандидат когда-либо попадал (дата, стрим, отправлен/не отправлен), новые сверху. Источник данных: `lib/db/mailing-lists.ts` → `getMailingListsForCandidate(candidateId)` — прямой запрос к `mailingListEntries` (TASK-DB-5) по `candidateId`, без похода в Sheets. Паттерн UI — тот же, что уже есть для истории резюме (TASK-32): подгрузка в `useEffect` при открытии модалки, без отдельного action на каждый выпуск.

*Что осталось от исходной формулировки* (правила 2–6, автоматизация поверх уже видимой истории):

* Статус «Не публиковать» — нет такого значения в `CandidateStatus` (`lib/sheets.ts`), сейчас только «На проверке» / «Активный» / «Отклонён».

NOTE: ℹ️ Стримы хранятся в Neon (TASK-DB-8 ✅). Global Config рассматривается как опциональная оптимизация: чтение из CDN-ноды за < 1 мс против ~50 мс запроса к Neon. UI управления стримами уже готов (`components/streams-table.tsx`) — задачи ниже касаются только смены бэкенда хранения, не UI.

Vercel Global Config (Edge Config) — глобально реплицированное key-value хранилище, читается прямо на CDN-ноде без обращения к серверу. Лимиты: 1 МБ, 100 000 чтений/мес, 100 записей/мес, задержка записи до 10 секунд.

==== TASK-GC-2: Замена getStreams() / getStreamsDetailed() на Edge Config

Заменить реализацию в `lib/db/streams.ts` — сигнатуры и все вызовы остаются прежними.

[source,ts]
----
import { get } from "@vercel/edge-config"

export async function getStreams(): Promise<string[]> {
  const streams = await get<StreamRecord[]>("streams")
  return (streams ?? []).map((s) => s.name)
}

export async function getStreamsDetailed(): Promise<StreamRecord[]> {
  return (await get<StreamRecord[]>("streams")) ?? []
}
----

Функции записи (`createStreamRecord`, `updateStreamRecord`, `deleteStreamRecord`) переключить на Edge Config API вместо Drizzle. Server Actions в `app/actions.ts` остаются без изменений.

*Сложность:* низкая.

==== TASK-GC-3: Адаптация Server Actions для записи в Edge Config

NOTE: ℹ️ UI управления стримами уже реализован в TASK-DB-8 (`components/streams-table.tsx`, Server Actions `createStream/updateStream/deleteStream`). TASK-GC-3 — только смена бэкенда записи с Drizzle/Neon на Edge Config API.

Заменить реализацию Server Actions в `app/actions.ts`:

[source,ts]
----
// Вспомогательная функция записи в Edge Config
async function updateStreamsInConfig(streams: StreamRecord[]): Promise<void> {
  await fetch(`https://api.vercel.com/v1/edge-config/${process.env.EDGE_CONFIG_ID}/items`, {
    method: "PATCH",
    headers: {
      Authorization: `Bearer ${process.env.VERCEL_API_TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ items: [{ operation: "upsert", key: "streams", value: streams }] }),
  })
}
----

Все три action-а (`createStream`, `updateStream`, `deleteStream`) читают текущий массив из Edge Config, вносят изменение и пишут обратно через `updateStreamsInConfig`. `revalidatePath` остаётся без изменений.

*Сложность:* низкая — только замена слоя хранения, UI не меняется.

NOTE: ℹ️ Задержка записи в Global Config — до 10 секунд до глобального распространения. Для управления стримами это несущественно.

== Приложение: переход на реляционную СУБД

=== Анализ

Google Sheets достаточен для MVP, но создаёт структурные ограничения по мере роста:

* *Производительность:* каждый запрос — HTTP-вызов к Sheets API; нет индексов, фильтрация только in-memory. При 500+ кандидатах и 100+ работодателях это станет ощутимым.
* *Целостность данных:* нет foreign keys и транзакций — связи между листами поддерживаются вручную (candidateId, employerToken — строки без ограничений).
* *Сложные запросы:* фильтрация, JOIN-подобные операции (подборка → кандидаты → работодатели) делаются in-memory в `lib/sheets.ts`, что увеличивает объём данных, которые нужно держать в памяти.
* *Параллельные записи:* append-only подход с `rowIndex` — хрупкий при одновременных операциях.
* *Лимиты API:* Google Sheets API — 300 запросов в минуту на проект.

Отдельный продукт Vercel: глобально реплицированное key-value хранилище, читается прямо на CDN-ноде в регионе пользователя — без обращения к серверу. Чтение < 1 мс, P99 ≈ 15 мс.
