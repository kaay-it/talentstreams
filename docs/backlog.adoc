==== ✅ TASK-32: История версий резюме в Neon

*Что сейчас было до этой задачи:* когда рекрутер загружал в `CandidateEditModal` новый файл резюме вместо старого (например, после того как кандидату помогли подправить или брендировать резюме), в Sheets просто перезаписывался URL — старый blob-файл в Vercel Blob не удалялся и никуда не девался, но и ссылки на него больше нигде не было: чистый мусор, накапливающийся в хранилище без возможности его найти или использовать.

*Решение:* вместо удаления старых файлов — хранить полную историю версий резюме кандидата отдельно, в Neon, и показывать её в редакторе. Google Sheets по-прежнему хранит только URL последней версии (используется на публичных страницах, в проксировании и т. д.) — ничего в этом контуре не поменялось.

* `lib/db/schema.ts` — новая таблица `candidateResumes` (`id` text/UUID, `candidateId` text, `kind` text — `"file"`/`"link"`, `filename` text, `url` text, `createdAt` timestamp). Миграция `lib/db/migrations/0002_harsh_tomorrow_man.sql`, применена к продовой Neon.
* `lib/db/resumes.ts` (новый файл) — `addResumeVersion(data)` (не пишет, если `candidateId` или `url` пустые — молча пропускает, не бросает) и `getResumeVersions(candidateId)` (новые сверху, `orderBy(desc(createdAt))`). Если `filename` не передан явно и `kind === "file"` — имя выводится из URL через `blobFilenameFromUrl()` (ниже), а не остаётся пустым; для `"link"` фолбэка нет — у ссылки нет «имени файла».
* `lib/sheets.ts` — `Candidate` дополнен `id: string` (то же самое поле `id`/UUID, что уже резолвилось через `HEADER_ALIASES` для `Profile`, просто не попадало в объект `Candidate`, используемый редактором) — нужен как стабильный ключ для истории версий в Neon.
* `lib/blob.ts` (новый файл) — `isOwnFileUrl(url)`: `true`, если URL указывает на собственный Vercel Blob — напрямую (хост оканчивается на `blob.vercel-storage.com`) или через свой прокси `/api/resume?url=<blobUrl>` (тот же паттерн, что уже валидировал `app/api/resume/route.ts` — константа `BLOB_HOST` вынесена сюда и переиспользована оттуда, вместо дублирования). Любой другой URL — «ссылка», введённая кандидатом/рекрутёром вручную. Там же `blobFilenameFromUrl(url)` — берёт последний сегмент пути (`resumes/1754460447259-a1b2c3d4.pdf` → `1754460447259-a1b2c3d4.pdf`); это сгенерированное имя файла в Blob, а не оригинальное имя, под которым кандидат загружал файл — Vercel Blob оригинальное имя нигде не хранит, `put()` вызывается уже с нашим сгенерированным путём.
* `app/actions.ts`:
** `registerCandidate()` — генерирует `id` (как и раньше, `crypto.randomUUID()`, не через внешний скрипт), после успешной записи строки сразу пишет первую версию резюме в `candidateResumes`, если `resumeUrl` не пустой. Благодаря синхронной генерации `id` в этой же функции первый файл кандидата тоже попадает в историю — не только последующие замены через редактор.
** `updateCandidate()` дополнен `candidateId` (обязателен), `resumeVersionChanged?: boolean` и `resumeFilename?: string` — если `resumeVersionChanged` и `resumeUrl` не пустой, пишет новую версию в `candidateResumes` после записи в Sheets. Клиент передаёт `resumeVersionChanged` только когда итоговый `resumeUrl` реально отличается от `candidate.resumeUrl` на момент открытия формы — редактирование прочих полей без изменения резюме новую версию не создаёт.
** `kind` (`"file"` / `"link"`) в обоих случаях вычисляется на сервере через `isOwnFileUrl(resumeUrl)`, а не берётся из клиента — клиент присылает только `resumeFilename` (для файла) и признак изменения; какой именно вкладкой пользовался человек в форме, на классификацию не влияет.

Восстановления/выбора конкретной старой версии как «текущей» из списка нет — список только для просмотра и скачивания, чтобы вернуть старый файл текущим, нужно перезалить его вручную.

==== ✅ Реальный текст ошибки при регистрации/редактировании работодателя

*Проблема:* при регистрации работодателя с уже занятым email форма вместо понятного текста показывала общую ошибку Next.js: «An error occurred in the Server Components render. The specific message is omitted in production builds…». Реальное сообщение («Работодатель с таким email уже зарегистрирован») было видно только в серверных логах (`digest`).

*Причина:* осознанное поведение Next.js — в production-сборке Server Actions отдают клиенту общий текст для любого `throw new Error(...)`, чтобы не утекали детали непредвиденных ошибок. Это ломает ожидаемые, «бизнесовые» ошибки валидации (дубликат email/телефона, пустые обязательные поля), которые как раз нужно показывать пользователю как есть.

*Решение:* `registerEmployer()` и `updateEmployer()` (`app/actions.ts`) теперь возвращают `{ ok: true } | { ok: false, error: string }` вместо `throw` для ожидаемых случаев валидации. `EmployerRegistrationModal`/`EmployerEditModal` читают `result.error` из возврата; `catch` оставлен только на непредвиденные сбои (сеть/БД) — там по-прежнему общий фолбэк-текст, что корректно.

NOTE: ℹ️ Тот же паттерн — `throw new Error()` для валидации ломает вывод сообщения в production — остаётся в других Server Actions (`registerCandidate`, `createCandidate` и т. д.), но там соответствующие ошибки либо уже гасятся клиентской валидацией (`required`-поля), либо не встречались на практике. Исправлено точечно там, где реально ломалось (дубликат email/телефона у работодателя).

==== ✅ Стримы: статус Активный/Архивный, защита переименования/удаления, история рассылок

*Почему:* стрим можно было свободно переименовать или удалить без каких-либо проверок — опасно для стрима, по которому уже реально уходили рассылки: SendPulse (книги подписчиков, сопоставление «уже отправлено» через `getCampaigns()`, паттерн `${stream} — ${date}`) завязан на точное имя, не на id. Переименование задним числом тихо ломает эту связь; удаление вводит в заблуждение — стрим пропадает из UI, а его прошлые рассылки остаются «ничейными».

* `lib/db/schema.ts` — `streams` дополнена колонкой `status` (`text`, дефолт `'Активный'`, второе значение — `'Архивный'`; по-русски, единообразно с `CandidateStatus`/`EmployerStatus`, а не буквально «Active/Archived»). Миграция `lib/db/migrations/0008_square_chimera.sql`.
* **Правило:** если у стрима уже есть **отправленная** рассылка — переименование и удаление недоступны, доступно только архивирование. Только *имя* защищено — тип и описание остаются редактируемыми всегда, для любого стрима (чисто информационные поля, `type` нигде не используется программно кроме цвета бейджа в UI, ничего вниз по цепочке на них не завязано).
* `app/actions.ts` — приватный `streamHasSentReleases(streamId)`: пересекает `getMailingLists()` (все выпуски стрима) с `getCampaigns()` (SendPulse) по имени кампании — тот же приём, что уже используют `deleteMailingList()`/`getCandidateMailingHistory()`. `updateStream(id, data)` бросает ошибку, если `data.name` отличается от текущего и `streamHasSentReleases` — true; `deleteStream(id)` — аналогично при удалении. Перепроверка на сервере — defense-in-depth, UI и так прячет недоступное действие (тот же принцип, что уже у `deleteMailingList()`). Новые `archiveStream(id)`/`unarchiveStream(id)` — без проверок, архивировать/восстановить можно всегда.
* `lib/db/streams.ts` — `getStreams()` (имена стримов, используется формой регистрации, `ReleaseCreateModal`, фильтрами/мультиселектами кандидата и работодателя) теперь фильтрует `WHERE status = 'Активный'` — архивный стрим по смыслу не должен предлагаться ни в одном из этих мест. Сигнатура не изменилась, ни один из 4 вызывающих файлов не тронут. `getStreamsDetailed()` (только для страницы стримов) — без фильтра, отдаёт все со `status`. Новая `getStreamById(id)`. `updateStreamRecord(id, data)` — тип данных стал `Partial<{name, type, description, status}>` (тот же приём, что `updateEmployerFields` при переносе работодателей — Drizzle `.set(data)` трогает только переданные поля, отдельная функция под статус не нужна).
* **Заодно — `mailingListEntries.stream` (text) → `streamId` (FK на `streams.id`, `ON DELETE SET NULL`):** решено сделать вместе, а не отдельной задачей. Как только имя «занятого» стрима стало неизменным правилом выше, главная причина держать денормализованный текст (риск дрейфа имени при переименовании — см. NOTE в TASK-DB-5 выше) снялась. Миграция в два прохода: A — добавить `streamId` (nullable), оставить `stream` (text) нетронутым, `npm run db:generate`+`migrate`; бэкафилл — один SQL `UPDATE ... FROM streams WHERE s.name = m.stream` (не построчный скрипт, одна команда на всю таблицу), скрипт `scripts/_backfill-stream-id.mjs` удалён после использования; B — убрать колонку `stream`, `generate`+`migrate` снова. Между A и B код уже читает/пишет через `streamId` (`join` на `streams` для отображения имени) — колонку `stream` можно уронить в любой момент после бэкафилла.
* `lib/db/mailing-lists.ts` — внешний контракт не изменился (`createMailingListRows({stream, date, candidateIds})` по-прежнему принимает **имя**, не id — резолвит через уже существующий `getStreamIdByName()` перед вставкой; `MailingList`/`MailingListSummary`/`CandidateMailingHistoryEntry` по-прежнему отдают `stream` строкой). ==== ✅ Дата выпуска фиксируется по факту первой отправки

*Почему:* дата в выпуске — это план, а не обязательство. Менеджер может собрать выпуск заранее на одну дату, а реально нажать «Отправить» в другой день (задержка, приоритеты и т. д.) — раньше карточка выпуска и тема письма продолжали показывать исходную плановую дату, даже если она разошлась с тем, что реально произошло.

* `app/actions.ts` — `publishMailingList(listId)`: перед формированием кампании проверяет через `getCampaigns()` (SendPulse), отправлялся ли этот выпуск уже (тот же паттерн `${stream} — ${date}`, что у `deleteMailingList()`/`streamHasSentReleases()`). Если это первая отправка и сегодняшняя дата (`todayIso()`, новый маленький helper) не совпадает с сохранённой — пишет новую дату в `mailingListEntries` (`updateMailingListDate(listId, date)`, `lib/db/mailing-lists.ts`) и использует её дальше для темы письма/имени кампании. Если выпуск уже отправлялся раньше (повторная отправка) — дата не трогается: тема и имя кампании остаются теми же, что были при первой отправке, кампания продолжает сопоставляться с историей.
* `lib/db/mailing-lists.ts` — `isoToRu()` (уже существовавший приватный форматтер даты) стал экспортируемым — переиспользован в `app/actions.ts` вместо ещё одной копии той же конвертации. Новая `updateMailingListDate(listId, date)` — прямой `UPDATE ... SET targetDate WHERE listId = ...`, та же форма, что у `deleteMailingListRows`/`createMailingListRows`.
* `revalidatePath("/editor")` добавлен в `publishMailingList()` — раньше экшен ничего не писал в Neon и обходился без него; теперь дата на карточке выпуска должна обновиться сразу после отправки.
* Проверено на реальных данных: создан тестовый выпуск с заведомо неверной плановой датой (25.12.2026), логика первой отправки (проверка `alreadySent` + сравнение с сегодняшней датой + запись в БД) прогнана напрямую по тем же функциям, что использует `publishMailingList()` — дата в Neon и на карточке `/editor` корректно заменилась на фактическую (24.09.2026); повторная отправка (симулирована — `alreadySent = true`) корректно не меняет дату. Реальный клик «Отправить» намеренно не выполнялся — создал бы настоящую кампанию SendPulse и реальное письмо подписчикам.

==== ✅ Мультиязычная главная страница (RU/EN)

*Почему:* главная страница (лендинг + формы регистрации кандидата/работодателя) — единственное, что видят внешние посетители сервиса, не говорящие по-русски. Редактор (`/editor/*`) сознательно не тронут — им пользуется только внутренняя команда.

==== ✅ Телефон кандидата: Google Sheets теряет «+» или считает номер формулой

*Почему:* Google Sheets автоматически трактует ячейку, начинающуюся с `+`/`-`/`=`, как начало формулы — номер `+998901234567`, введённый прямо в таблицу (вручную или через форму сайта), под капотом превращается в `=+998901234567`. Обычное чтение через Sheets API (`FORMATTED_VALUE`, использовалось везде) в лучшем случае тихо теряет `+` (унарный плюс — просто число), в худшем — если в номере есть пробелы/дефисы (`+375-29-195-79-3`) — Sheets пытается посчитать это как арифметику и выдаёт либо `#ERROR!`, либо совершенно другое число. На реальных данных это ударило по 125 из 164 кандидатов (потерян `+`), включая минимум 4 по-настоящему испорченных: два показывали буквально `#ERROR!` вместо телефона, один превратился в `"69"` (Sheets посчитал `375-29-195-79-3` как `375−29−195−79−3`), другой — в `"-1475"`.

* `lib/sheets.ts` — `fetchSheetValues()` научилась принимать необязательный `valueRenderOption` (`FORMULA` — сырой текст формулы, а не её результат). Новая `recoverPhoneColumn(sheetId, values)`: по заголовкам находит колонку «Phone» (через тот же `mapHeader()`, что и остальной маппинг), отдельным узким запросом (только эта колонка, не весь лист) тянет её с `valueRenderOption=FORMULA`, снимает ведущий `=` у каждой ячейки — это и есть то, что реально было напечатано, независимо от того, как Sheets это интерпретировал. При сбое второго запроса — тихий откат к исходным (возможно, сломанным) значениям, не валит основное чтение.
* Подключено во все функции чтения кандидатов: `getProfiles()`, `getProfile()`, `getCandidates()`, `getSheetTable()`. Чинит и уже испорченные строки (сколько бы лет они так ни пролежали), и строки, вписанные вручную прямо в Google-таблицу — не только через форму регистрации сайта.
* Проверено на реальных данных: diff-скрипт, сравнивший старое/новое значение телефона по всем 164 кандидатам, показал ровно предсказанную картину (125 номеров восстановили потерянный `+`, 4 — восстановили исходный текст вместо ошибки/мусора); в `/editor/candidates` через Playwright подтверждено, что ранее битая строка (`#ERROR!`) теперь показывает корректный номер и `#ERROR!` нигде на странице не осталось.

==== ✅ TASK-38: Уникальность email/телефона у кандидатов и работодателей

*Почему:* `candidates.email`/`phone` не имели никакой проверки на дубли — можно было зарегистрироваться сколько угодно раз с одним и тем же email. *Реальные данные перед миграцией (`candidates`):* 8 кандидатов с пустым email, 11 с пустым телефоном (легаси/плейсхолдеры из исходной Google-таблицы, см. TASK-DB-4), 5 пар кандидатов с совпадающим email или телефоном — все оказались повторной отправкой формы одним и тем же человеком (опечатка в email, вторая попытка с улучшённым сопроводительным письмом, обновлённое резюме). Разобраны вручную по каждой паре отдельно: где просто повторная отправка — удалена старая/лишняя строка (через `/editor/candidates`, чтобы заодно почистился файл в Vercel Blob, если резюме было загружено, а не ссылкой); где обе заявки несли разные полезные данные (отдельное резюме, отдельный текст сопроводительного письма) — профили объединены (резюме перенесены на одну запись через `UPDATE candidateResumes SET candidateId = ...`, тексты сопроводительных писем склеены). `employers.email`/`phone` — 0 пустых, 0 дублей, никаких подготовительных действий не потребовалось.

* `candidates.email`/`candidates.phone` — стали nullable (`DROP NOT NULL`/`DROP DEFAULT`, легаси `''` забэкафилены в `NULL` одним `UPDATE`) + `UNIQUE`. Nullable обязательно для `UNIQUE` на необязательном поле — Postgres никогда не считает два `NULL` равными, а два `''` считал бы дублями, что сломало бы запись первого же второго кандидата без телефона. `employers.email`/`phone` — уже всегда заполнены (оба обязательны при регистрации), добавлен только `UNIQUE`, без изменения nullability.
* `lib/db/candidates.ts` — `email`/`phone` конвертируются `null ↔ ""` на границе модуля (`toCandidate()`, `createCandidateRecord()`, `updateCandidateFields()`), тот же приём, что уже у `activeSince`/`contactRequests.candidateId` — внешний тип `Candidate.email`/`phone` остаётся `string`.
* **`registerCandidate()`/`createCandidate()`/`updateCandidate()` переведены с `throw new Error(...)` на `{ ok, error }`** — тот же паттерн, что уже у `registerEmployer()`/`updateEmployer()`, и по той же причине (комментарий в коде уже объяснял: «Next.js redacts thrown Error messages from Server Actions in production builds»). Без этого новое сообщение «Кандидат с таким email уже зарегистрирован» в продакшене подменялось бы на обобщённую ошибку Next.js — то есть вся работа по дружелюбному сообщению была бы не видна пользователю. Заодно это исправило эту же проблему и для уже существующих проверок («Укажите имя»/«Укажите email»), которые раньше бросали исключение. Три вызывающих компонента (`candidate-registration-modal.tsx`, `candidate-create-modal.tsx`, `candidate-edit-modal.tsx`) обновлены читать `result.ok`/`result.error` вместо try/catch вокруг самого вызова действия (try/catch остался только вокруг загрузки файла).
* Нарушение `UNIQUE` (код Postgres `23505`) отличается по `err.cause.constraint` (`candidates_email_unique`/`candidates_phone_unique`/`employers_email_unique`/`employers_phone_unique`) — общий приватный хелпер `uniqueViolationConstraint()` в `app/actions.ts` достаёт это из `err.cause` (драйвер `neon-http` оборачивает исходную ошибку Postgres), остальное пробрасывается дальше как есть.
* `registerEmployer()`/`updateEmployer()` дополнены тем же `try/catch` как подстраховка на случай гонки, которую существующая проверка (только среди активных, с нормализацией) теоретически может пропустить — обычным путём туда не попасть, но теперь есть и защита на уровне БД.
* Заодно убран `DEFAULT ''` у `employers.name`/`email`/`phone`/`primaryContact`/`country` (остались `NOT NULL`, без default) — все пять всегда валидируются и передаются явно в `registerEmployer()` до записи, `''` для них никогда не было реальным состоянием, только нетронутый шаблон со старого «у каждой text-колонки `NOT NULL DEFAULT ''`». Без default будущий баг, забывший передать одно из этих полей, упадёт на `NOT NULL`-ограничении БД, а не тихо запишет пустую строку. `telegram`/`linkedin` default не трогали — там `''` законное состояние (работодатель мог выбрать другой способ связи).

==== ✅ TASK-42: `mailingListEntries.candidateId` — `ON DELETE SET NULL` → `ON DELETE CASCADE`

*Почему:* `candidateId` был `ON DELETE SET NULL` с заявленной целью «история рассылок переживает удаление кандидата». На практике это не работало — каждая читающая функция (`getMailingList()`, `getMailingListCandidateIds()`, `getMailingLists()`) и так отфильтровывала строки с `NULL candidateId` перед подсчётом `candidateCount`/`candidateIds`, так что сохранённая строка никогда не была видна ни в одном месте приложения — только раздувала сырой `COUNT(*)` мимо того, что показывал UI, и не несла идентичность удалённого кандидата (после `SET NULL` нельзя сказать, кто это был). `ON DELETE CASCADE` убирает эту тихую рассинхронизацию без изменения видимого поведения приложения — колонка заодно стала `NOT NULL` (на момент миграции осиротевших строк не было, 0 из 24).

* Та же логика, что уже применена к `listId` этой же таблицы (`ON DELETE CASCADE` — строка `mailingListEntries` не имеет смысла без родителя) и к `candidateResumes.candidateId` — запись «кандидат участвовал в этом событии» не переживает удаление самого кандидата осмысленно, в отличие от, например, `contactRequests.candidateId` (запрос работодателя остаётся осмысленным даже без привязки к конкретному кандидату — это другой случай, не трогали).
* Миграция (`lib/db/migrations/0020_mailing-entries-candidate-cascade.sql`) — чистая, автосгенерированная `drizzle-kit generate` без ручной правки (не рефакторинг/переименование колонки, а только смена `ON DELETE` + `SET NOT NULL`, которые `generate` понимает однозначно): `DROP CONSTRAINT` + `ALTER COLUMN SET NOT NULL` + `ADD CONSTRAINT ... ON DELETE CASCADE`.
* `lib/db/mailing-lists.ts` — убраны три теперь заведомо лишних `.filter(id => Boolean(id))`/`if (row.candidateId)` (в `getMailingList()`, `getMailingListCandidateIds()`, `getMailingLists()`) — `candidateId` больше не может быть `null` в выборке, фильтрация ничего не делала бы, кроме как маскировать то, что колонка уже гарантирует на уровне БД.
* Проверено на реальных данных: 0 осиротевших строк перед миграцией (бэкафилл не понадобился); функциональный тест скриптом — тестовый кандидат в тестовом выпуске, прямое удаление кандидата (`deleteCandidateRecord()`) корректно каскадно удаляет его строку `mailingListEntries` (было 1, стало 0).

==== ✅ TASK-43: Гонка при отправке ограниченной рассылки + крон-очистка одноразовых SendPulse-книг

*Почему:* реальная попытка отправить ограниченную рассылку упала с `error_code 798` («В адресной книге нет подписчиков»), хотя выбранный получатель — давно подтверждённый работодатель. Прямым тестом против API SendPulse подтверждено: `POST /addressbooks/{id}/emails` отвечает `200 {"result":true}`, но добавленный адрес не всегда сразу виден проверке «книга не пуста» внутри `POST /campaigns` — задержка индексации на стороне SendPulse может доходить до нескольких секунд. `publishMailingList()` вызывал `createCampaign()` буквально через ~10мс после ответа на добавление в книгу, без какой-либо паузы.

* **Часть 1 — ретрай на гонку индексации.** `createCampaign()` (`app/actions.ts`) при `error_code: 798` делает до 3 повторов с паузой 0.5с/1с/1.5с (1.5с суммарно), прежде чем отдать финальную ошибку. Паузы специально небольшие: Server Action выполняется как serverless-функция Vercel с жёстким лимитом 10с на Hobby-плане (`maxDuration` там не поднять) — более долгий ретрай рисковал бы упереться в этот лимит поверх остальной сетевой работы публикации.
* **Часть 2 — одноразовая книга не удалялась после отправки.** После того как ретрай решил проблему 798, обнаружилось следующее: `publishMailingList()` удалял одноразовую SendPulse-книгу ограниченной рассылки сразу в `finally` после `createCampaign()`, в том числе на успешном пути. Но реальная кампания после создания уходит на модерацию SendPulse («Статус рассылки: Рассылка на модерации») на непредсказуемый срок — а SendPulse не даёт удалить книгу, пока она привязана к незавершённой кампании; попытка молча проваливалась (`deleteAddressBook()` — best-effort, ошибки только логируются) и больше никогда не повторялась. Подтверждено на реальных данных: после фактической отправки (`campaign.status === 3`, `statistics.sent: 1`) книга осталась висеть в SendPulse нетронутой.
** Блокирующий `await` внутри самого запроса не вариант — модерация может занять неизвестное время, явно больше 10с лимита функции.
** Решение — отдельный **ежедневный Vercel Cron** (`vercel.json`, `app/api/cron/cleanup-adhoc-books/route.ts`): находит в Neon отправленные ограниченные выпуски (`getSentRestrictedMailingLists()` — `sentCampaignId IS NOT NULL AND recipientLabel != ''`, только они вообще когда-либо получают одноразовую книгу), спрашивает статус кампании у SendPulse (`getCampaignStatus()`, `GET /campaigns/{id}`) — при `status === 3` (единственное значение, подтверждённое прямым тестом на всех реально отправленных кампаниях аккаунта как «полностью обработано») ищет книгу по имени и удаляет её. Best-effort на каждый элемент — одна неудача не останавливает обход остальных, в худшем случае просто попробует на следующий день.
** `publishMailingList()` теперь удаляет одноразовую книгу немедленно только на пути ОШИБКИ (`createCampaign()` бросил — кампания не создалась, книга ничем не занята, удаление реально проходит); на успешном пути книгу больше не трогает вовсе, оставляя это крону.
** Роут защищён `CRON_SECRET` (`Authorization: Bearer <значение>` — именно так Vercel Cron подписывает свои запросы); без переменной окружения роут открыт (локальная разработка).
* Проверено на реальном зависшем выпуске («Tech — 25.10.2026 — IT Improve», уже отправлен): первый запуск крона нашёл книгу, подтвердил `status: 3`, удалил; повторный запуск корректно увидел «already gone» — идемпотентно.

==== ✅ TASK-44: Подборки — отдельный раздел редактора, отделены от рассылки; выпуск только выбирает их

*Почему:* до этой задачи один `listId` одновременно означал и «кому физически уйдёт письмо» (`mailingListRecipients`, TASK-40 — узкая SendPulse-книга либо весь стрим), и «какой фиксированный набор кандидатов увидит любой, кто перейдёт по ссылке» (`mailingListEntries`, с гео-фильтром поверх). Персонализация контента для РАЗНЫХ работодателей ОДНОГО стрима в рамках ОДНОЙ рассылки была невозможна — только через отдельное узкое письмо. Менеджеру нужно: готовить общую (дефолтную) и личные подборки отдельно от конкретного выпуска, заранее, и собирать из них рассылку просто выбором, без создания/правки состава на месте.

*Решения, принятые с пользователем (в порядке обсуждения):*
. Попадание кандидата в любую подборку рассылки (дефолтную или личную) засчитывается в счётчик «отправлено N раз» (TASK-05) один раз — не по разу за подборку.
. Личная подборка полностью обходит `filterCandidatesForEmployer` — ни гео-фильтр, ни `excludedCompanies`/`excludedStreams` кандидата не применяются: менеджер вручную отобрал кандидатов для конкретного работодателя, подстраховка не нужна. Фильтр остался только для дефолтной подборки.
. Дефолтная подборка опциональна — у рассылки может не быть дефолтной вовсе, если менеджер подготовил личные подборки на всех подписчиков стрима без исключения; работодатель без применимой подборки видит состояние «Подборка для вас пока не готова» (не 404 — письмо он всё равно мог получить).
. Оба механизма (узкая SendPulse-книга TASK-40 и личные подборки) — независимые оси, оставлены оба: одно не заменяет другое.
. **Пересмотрено по ходу работы** — изначально подборки создавались и редактировались прямо в модалке выпуска (как черновик TASK-44 первой итерации). Решено иначе: подборки готовятся заранее в отдельном разделе редактора «Подборки», привязанные к стриму, но ещё без конкретного выпуска; при создании/редактировании рассылки их только выбирают (чекбоксом), никогда не создают и не редактируют на месте.
. Подборка, выбранная в рассылку — «присоединяется» (attach) к ней. Убрать её из ещё не отправленного выпуска — не удаление, а открепление (detach): подборка возвращается в пул и может быть выбрана в другую рассылку позже. Подборка, прикреплённая к уже отправленному выпуску, открепить нельзя (история).
. Состав подборки (кандидаты/работодатели) редактируется только в разделе «Подборки» — независимо от того, прикреплена она сейчас к неотправленному выпуску или свободна в пуле. Сторона выпуска — чистый выбор, никогда не редактирование состава.
. Менеджеру при подготовке рассылки всегда показывается таблица-ростер «кому что попадёт» (не условный баннер — сама таблица одновременно и показывает распределение, и предупреждает, подсвечивая работодателей без подборки). При отправке, если среди получателей есть работодатель без дефолтной и без личной подборки, требуется явное подтверждение.
. Просматривать имеет смысл подборку саму по себе — у неё есть собственная страница, редактор может открыть любую напрямую, независимо от того, прикреплена она к выпуску или свободна.
. **Донастроено по ходу работы** — в разделе «Подборки» по умолчанию видны подборки ВСЕХ стримов разом, не одного за раз: фильтр по стриму остался, но превратился из обязательной навигации («сначала выберите стрим») в опциональное уточнение («Все» — активен по умолчанию). В таблице теперь видно, какому стриму принадлежит каждая строка (бейдж), раз они теперь могут быть вперемешку.
. У подборки появилась собственная дата (`targetDate`), задаётся при создании и редактируется отдельно от даты выпуска, в который подборку в итоге заберут — форма создания повторяет порядок полей, который раньше был у выпуска: сначала стрим, потом дата, потом состав.

*Что сделано теперь (второй инкремент — сама пауза, автоматически):*

* *Решение по хранению:* обсуждали хранить паузу отдельными полями дат (1-я/2-я публикация) или одним `activeSince`, пересчитываемым на лету по реальной истории рассылок при каждой загрузке `/editor`. Запись — через уже существующую `updateCandidateStatus(rowIndex, status, activeSince)`, для чего понадобился `rowIndex`: он есть только в `getCandidates()` (полный список, все статусы), не в `getProfiles()`.

Кандидаты со статусом `"Не публиковать"` в этот список никогда не попадают — они уже отфильтрованы на уровне `getProfiles()`. В обоих списках (подходящие и на паузе) рядом с каждым кандидатом теперь показана дата `activeSince` — для наглядности, почему кандидат вообще в том или ином списке.
* `components/candidate-section.tsx` — статус `"Не публиковать"` показан отдельным (розовым) бейджем на странице «Кандидаты», добавлен в фильтр статусов; кнопка «Подтвердить» (уже существовавшая для статуса «Отклонён») переиспользована и для `"Не публиковать"` — иначе кандидат, ушедший в этот статус автоматически, не имел бы способа вернуться в рассылки через UI вообще. Возвращает статус в `"Активный"`, сохраняя текущую `activeSince` (+10 лет) — редактор поправляет дату отдельно через «Редактировать», как и раньше для любого кандидата.

*Что осталось от исходной формулировки:*

* «Кандидат может попросить статус «Не публиковать»» — прямого способа поставить этот статус *по запросу* кандидата (а не только автоматически после 3-й отправки) в UI нет; сейчас это можно сделать только в обход интерфейса, напрямую в Google Sheets.

Отдельно через Playwright проверены оба UI: схлопнутый список «на паузе» с датами и рабочими чекбоксами в `ReleaseCreateModal`, и на странице «Кандидаты» — бейдж, фильтр и кнопка «Подтвердить», возвращающая кандидата в «Активный». === 🔵 Опционально — Vercel Global Config для стримов

NOTE: ℹ️ Стримы хранятся в Neon (TASK-DB-8 ✅). Global Config рассматривается как опциональная оптимизация: чтение из CDN-ноды за < 1 мс против ~50 мс запроса к Neon. UI управления стримами уже готов (`components/streams-table.tsx`) — задачи ниже касаются только смены бэкенда хранения, не UI.

Vercel Global Config (Edge Config) — глобально реплицированное key-value хранилище, читается прямо на CDN-ноде без обращения к серверу. Лимиты: 1 МБ, 100 000 чтений/мес, 100 записей/мес, задержка записи до 10 секунд.

import { get } from "@vercel/edge-config"

==== TASK-GC-3: Адаптация Server Actions для записи в Edge Config

NOTE: ℹ️ UI управления стримами уже реализован в TASK-DB-8 (`components/streams-table.tsx`, Server Actions `createStream/updateStream/deleteStream`). TASK-GC-3 — только смена бэкенда записи с Drizzle/Neon на Edge Config API.

Заменить реализацию Server Actions в `app/actions.ts`:

[source,ts]
----
// Вспомогательная функция записи в Edge Config
async function updateStreamsInConfig(streams: StreamRecord[]): Promise<void> {
  await fetch(`https://api.vercel.com/v1/edge-config/${process.env.EDGE_CONFIG_ID}/items`, {
    method: "PATCH",
    headers: {
      Authorization: `Bearer ${process.env.VERCEL_API_TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ items: [{ operation: "upsert", key: "streams", value: streams }] }),
  })
}
----

Все три action-а (`createStream`, `updateStream`, `deleteStream`) читают текущий массив из Edge Config, вносят изменение и пишут обратно через `updateStreamsInConfig`. `revalidatePath` остаётся без изменений.

== Приложение: переход на реляционную СУБД

=== Анализ

Google Sheets достаточен для MVP, но создаёт структурные ограничения по мере роста:

* *Производительность:* каждый запрос — HTTP-вызов к Sheets API; нет индексов, фильтрация только in-memory. При 500+ кандидатах и 100+ работодателях это станет ощутимым.
* *Целостность данных:* нет foreign keys и транзакций — связи между листами поддерживаются вручную (candidateId, employerToken — строки без ограничений).
* *Сложные запросы:* фильтрация, JOIN-подобные операции (подборка → кандидаты → работодатели) делаются in-memory в `lib/sheets.ts`, что увеличивает объём данных, которые нужно держать в памяти.
* *Параллельные записи:* append-only подход с `rowIndex` — хрупкий при одновременных операциях.
* *Лимиты API:* Google Sheets API — 300 запросов в минуту на проект.

=== Рекомендация

*На этапе разработки и раннего MVP* — Neon Free + Vercel Blob Hobby. Никаких дополнительных расходов, нет паузы проекта, резюме хранятся в Vercel Blob (1 ГБ хватит на сотни файлов).

*При регулярном ежедневном трафике* (появились реальные клиенты) — апгрейд Neon до Launch ($19/мес). Vercel Blob Hobby, скорее всего, продолжит покрывать потребности.

*Против Supabase:* при хостинге на Vercel Supabase становится лишним сторонним сервисом — отдельный аккаунт, отдельный счёт, ручная настройка env vars. Преимуществ перед Neon+Blob нет: оба дают PostgreSQL + файловое хранилище, но Neon нативно интегрирован в Vercel.

*Технический выигрыш от перехода:* `lib/sheets.ts` (1039 строк, весь header-mapping и `ensureColumns`-код) заменяется на `lib/db/` с Drizzle — схема на TypeScript, SQL-like запросы, минимальный бандл без cold-start штрафа на Vercel. История версий резюме (TASK-32) реализуется через `@vercel/blob`.

=== Схема данных (PostgreSQL)

[source,sql]
----
candidates       -- профили + регистрации (текущий главный лист)
  id UUID PK, name, title, email, phone,
  stream, level, industry, func, country_primary, country_desired,
  summary, excluded_companies TEXT[], excluded_industries TEXT[],
  status, active_since, registration_timestamp, cover_letter, resume_url

employers        -- работодатели
  id UUID PK, timestamp, name, company, email, phone,
  telegram, linkedin, primary_contact, streams TEXT[],
  country, additional_countries TEXT[], status

streams          -- список стримов
  id SERIAL PK, name TEXT UNIQUE, type TEXT NOT NULL DEFAULT '', description TEXT NOT NULL DEFAULT ''

mailing_lists    -- выпуски
  id UUID PK, stream, date
mailing_list_candidates   -- связь выпуск ↔ кандидат
  list_id UUID FK, candidate_id UUID FK

contact_requests -- запросы на контакт
  id UUID PK, timestamp, list_id UUID FK, stream,
  candidate_id UUID FK (nullable — общий запрос),
  employer_id UUID FK, employer_name, company, employer_email, status
----
